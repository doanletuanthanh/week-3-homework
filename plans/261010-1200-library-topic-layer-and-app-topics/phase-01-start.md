# Phase 1: Topic data and library queries

## Overview

The columns, the topic file fields, the queries and the events that Màn 2, Màn 2b and the next-persona suggestion read. No screen changes here.

## Context links

- PRD §4, §7, FR-4, FR-31, FR-38, FR-50; canvas note `d1` (`docs/design/artboards/canvas.json`).
- Existing: `src/db/schema.ts` (`topics`, `users`), `src/scenario/schema.ts` (`topicSchema`), `src/db/repo/scenarios.ts` (`upsertTopic`), `src/db/repo/sessions.ts` (`getPlayableScenario`, `visibleTo`, `findSessionForPersona`), `src/server/events.ts`, `src/server/session-list.ts` (`STATE_OF`).

## Requirements

- Functional:
  - A topic has a role (`ux` | `ba` | `pm` | none) and a display order; both come from `topic.json`.
  - A learner's role filter (`ux` | `ba` | `pm` | `other` | none) is stored on the account.
  - One query lists curated topics that have at least one playable persona, in display order, with the persona count and, for a signed-in learner, how many of them have a `done` session.
  - One query returns a topic with its playable personas and, per persona, the learner's newest counting session (not `withdrawn`).
  - One query lists the learner's own custom topics, newest first, each with the state of its playable session, or of its newest attempt when there is none.
  - One function picks the next persona (FR-31).
  - Two new events: `role_filter_selected`, `topic_opened`.
- Non-functional:
  - Nothing here selects `scenario.content` whole into a value that a page passes to the browser. The item count is read in SQL (`jsonb_array_length(content->'items')`).
  - A custom topic is visible to its owner only (same `visibleTo` rule).

## Architecture

- Migration `0012_topic-role-and-order.sql` (generated by `pnpm db:generate`): `topic.role text NULL`, `topic.display_order integer NOT NULL DEFAULT 0`, `user.role_filter text NULL`. Backfill in the same migration: `UPDATE topic SET role = 'ux' WHERE id = 'ux-chi-tieu'`.
- `topicSchema` gains `role: z.enum(["ux","ba","pm"])` and `display_order: z.number().int().min(0)`, both required (user decision 2026-10-10 after the phase review): an import writes every field of the file over the stored topic, so a file without one is refused instead of wiping it. `upsertTopic` writes both on insert and on conflict. Custom topics do not go through this schema and keep `role = NULL` (FR-52).

- `src/db/repo/library.ts`:
  - `listLibraryTopics(db, { requirePublished, userId })` → `{ id, title, summary, role, personaCount, doneCount }[]`. "Playable" is the newest version per `persona_id` under the `getPlayableScenario` predicate; export that predicate from `sessions.ts` instead of copying it.
  - `getTopicWithPersonas(db, topicId, { requirePublished, viewerId })` → topic + `{ personaId, name, displayName, tagline, avatarKey, researchGoal, itemCount, origin }[]`, or null when the topic does not exist or is someone else's custom topic.
  - `listSessionsForPersonas(db, userId, personaIds)` → newest non-withdrawn session per persona: `{ id, status, endedAt, startedAt }`.
  - `listOwnCustomTopics(db, userId)` → topic id, title (the text typed), created at, playable session or newest attempt. A topic whose chosen session is `withdrawn` (scenario taken down) is left out (user decision 2026-10-10); the stopped session stays in "Buổi của tôi".
- `src/server/library.ts`:
  - `personaButton(session)` → `"start" | "continue" | "review"`, built on `STATE_OF` from `session-list.ts` so §7 has one mapping. `STATE_OF` is a private constant today: export it.
  - `pickNextPersona(db, { userId, topicId, topicRole, roleFilter, requirePublished })` → `{ kind: "next", persona } | { kind: "all_practised" } | { kind: "none_exist" }`. Candidates: the playable personas of the same topic, then of the other curated topics of the same role; for a custom topic (no role) the learner's filter stands in, and no role means every topic. There is no fallback across roles (FR-31 and the string "của vai trò này"). No candidate at all → `none_exist`; candidates but all practised → `all_practised` (user decision 2026-10-10: never say "đã luyện mọi persona" about a role that has none). "Unpractised" = no counting session at all, and not in the tombstone's played list. Personas keep the order of their first import, whatever version is newest.
- `AppEvent` gains `{ name: "role_filter_selected"; props: { role: "ux"|"ba"|"pm"|"other"|null } }` and `{ name: "topic_opened"; props: { topic_id: string; kind: "curated"|"custom" } }`.
- Both events are written for signed-in learners only (user decision 2026-10-10): a guest's filter choice or page load writes nothing to the database. This narrows FR-50 and FR-38; `plan.md` lists it as a deviation.
- `src/db/repo/users.ts`: `setRoleFilter(db, userId, role)`.

## Risk assessment

- **Sealed content in a list query.** A `select()` of the whole scenario row would carry items to a server component and could be serialised to a client component. Mitigation: the repo returns named columns only; the test above.
- **`require_published` flipped on later.** Topics with only drafts then vanish from the library. That is the intended gate; note it in `docs/operations.md` (phase 6).
- **Rollback:** the migration only adds nullable or defaulted columns; reverting the code leaves them unused.
